# Wallets and RPC

1. Install the APK on Android 7 (API 24) or later. API 24 is the minimum declared in the manifest; startup has been verified on an API 37.2 emulator and an Android 16 phone. API 24 device testing remains pending.
2. Connect an installed Android wallet compatible with Mobile Wallet Adapter (MWA).
3. Lifeboat connects to Solana mainnet-beta through the public endpoint `https://api.mainnet.solana.com`. No API key or RPC selection is needed in the app yet.

Lifeboat supports external wallets only. It cannot import JSON keypairs or sign with a stored wallet key. The external wallet retains its private key; Lifeboat saves its address and MWA authorization token for reconnection. **Disconnect wallet** deletes that authorization. The app saves the RPC URL for submitted transactions with uncertain status, so status checks use the original endpoint.

A key copy saved by an older Lifeboat version remains in the private app directory, including any interrupted-write file. This version does not read, use or delete those files. The original user-selected JSON file is also untouched. Existing external authorizations and pending operation records remain usable after updating. Do not share app data containing authorization tokens or legacy keys.

MWA uses `solana:mainnet`. The external wallet must support `signTransactions`; `signAndSendTransactions` is not used. If authorization expires, the app requests access again and checks that the address has not changed. Compatibility depends on the wallet implementation and should be checked on the device.

Lifeboat accepts the exact message it simulated and showed for approval, or a response that passes the explicit bounded wallet-addition policy described below. On October 5, 2026, an earlier Claim ORE test through Solflare 2.29.1 returned an expanded transaction (1 instruction became 5, including 2 added Compute Budget instructions). The strict diagnostic build rejected it before submission. This identified a compatibility issue in that tested signing path, rather than an Ed25519 or network-confirmation failure. The subsequent investigation and compatibility policy are recorded below.

On the same date, the user confirmed successful Claim ORE from Lifeboat with Jupiter as the external wallet. Device diagnostics verified signing, unchanged-message and signature validation, RPC submission, and network confirmation. The returned message retained the original 412-byte legacy structure with 11 accounts and 1 instruction. This is a verified working path for the tested operation and device/build. Subsequent Phantom signing evidence and the remaining confirmation and Solflare device checks are recorded below. No project identity URI was configured for this successful attempt.

A later Solflare diagnostic attempt preserved the original Claim ORE instruction and appended a 240,000-unit compute limit, a 100,000-micro-lamport unit price, and two Lighthouse instructions: `AssertAccountInfoMulti` and `AssertTokenAccountMulti` (discriminators 6 and 10). The priority-fee component is 0.000024 SOL. These added instruction types are account assertions; their exact condition values were not captured by that diagnostic version. That build rejected the changed message before submission.

The subsequent compatibility update permits bounded Compute Budget settings and fully decoded Lighthouse assertion variants 6/10 while preserving the original operation instructions, accounts and signing context. The returned message's signatures and simulation postconditions are checked before a second fee review; choose **Send transaction** to submit that already signed version. The priority-fee cap is 0.0002 SOL per transaction; original operation costs and rent are separate. Unrecognized additions remain rejected. See the [policy and device-test matrix](solflare-validation.md) for exact limits and observed results; pending device rows are not verified wallet compatibility.

Claim SOL currently includes only rewards already recorded in Miner. The October 6 investigation confirmed a wallet with zero recorded SOL and 0.000013464 SOL pending from an eligible completed round; unsigned Checkpoint simulation matched the site's amount and paid the wallet directly because auto-return was enabled. Lifeboat does not yet settle such rounds. See [recorded and pending ORE SOL](ore-sol-rewards.md) for the evidence and required execution changes. This display/availability gap is separate from external-wallet signing compatibility.

Choosing **Connect wallet**, **Connect**, or **Switch wallet** directly starts a fresh authorization without the saved token or a pinned wallet URI. This allows Android to offer its wallet chooser and lets the wallet request connection approval. Saved authorization is reused only for signing. Wallets control the exact approval UI. A cancelled or failed connection retains the previously saved wallet.

During signing, a fresh connection prompt is requested only when token reuse fails with MWA `ERROR_AUTHORIZATION_FAILED`. Other errors stop the attempt. Renewed authorization is checked against the expected account and saved before the signature request; a later signing refusal does not discard that renewal. `ERROR_NOT_SIGNED` means the wallet declined to sign for some reason and does not necessarily mean the user pressed Cancel.

If the wallet opens without a connection request, check whether Android battery saver is enabled. On October 5, 2026, the user confirmed that disabling it restored connection on their phone: Solflare explained the battery saver issue, while Phantom did not. This observation establishes connection on that device; transaction approval still needs separate verification.

If Phantom opens without a connection request, return to Lifeboat and read the status message. A session failure means MWA did not establish communication with the wallet; unlock the wallet and retry, then check the wallet version if it persists. An authorization failure means the session started but access was not granted. Connection errors identify the failed step without exposing authorization tokens. The October 6 installation used only the name `Lifeboat`. On October 7, the project page was published at [ebartosh.github.io/lifeboat](https://ebartosh.github.io/lifeboat/) and its URI was configured locally for a comparison build. `identity.uri` is optional in the [MWA specification](https://solana-mobile.github.io/mobile-wallet-adapter/spec/spec.html), but recommended for identity verification. Do not substitute a website belonging to another app.

To configure an owned project website, set `EXPO_PUBLIC_WALLET_IDENTITY_URI` to its public HTTPS page URL and follow the [identity-verification experiment](wallet-identity/README.md). The code default remains name-only without configuration. The current project-path JSON is accessible at `/lifeboat/.well-known/assetlinks.json`, but the required origin-root `/.well-known/assetlinks.json` returns 404. This comparison therefore tests adding a real project-page URI; it does not establish Digital Asset Links verification. Setting a URI alone is not proof of trust or successful signing.

Open **Wallet details > Wallet signature check > Sign memo without sending** to request a legacy memo signature with a fresh mainnet blockhash. Lifeboat verifies the expected signature and unchanged message locally; it never submits this transaction or records it as pending. No network fee is paid. The check uses the same saved authorization and renewal path as Claim ORE. See [Phantom diagnostics](phantom-validation.md) for the comparison procedure and interpretation.

On October 6, two Phantom 26.31.1 memo checks also returned -1 during token reuse, accepted fresh authorization, and returned -3 during signing before any signed response. The refusal therefore extends beyond ORE instructions. The exact wallet-side reason remains unknown; no memo transaction was submitted.

On October 7, a Claim ORE attempt with the configured project-page URI did return a Phantom signature. Its bounded Compute Budget/Lighthouse additions passed policy, signature checks and repeat simulation. Reuse still needed fresh authorization after -1. After the updated-fee review, the blockhash expired and Lifeboat stopped before RPC submission. Signing is now observed for this attempt; successful Claim ORE confirmation is not yet established. The wallet's displayed host `ebartosh.github.io` corresponds to the selected URI's host.
